# Техническое задание: doxdix

## 1. Назначение

**doxdix** — локальный CLI-инструмент для автоматической генерации и актуализации документации проекта с помощью LLM. 

Инструмент пофайлово обходит исходный код, чтобы не переполнять контекстное окно LLM, и поддерживает существующую документацию: читает её, сверяет с кодом, актуализирует, сохраняя вручную написанные разделы. Перед изменениями создаёт бэкап.

**Ключевые архитектурные решения:**
- **Два режима LLM:** поддержка как нативного Ollama API (`/api/*`), так и любого OpenAI-совместимого endpoint (`/v1/*`: vLLM, LM Studio, OpenRouter, DeepSeek, opencode).
- **Защита от галлюцинаций:** передача `project_context` (первые 2000 символов из README) в промпты генерации SUMMARY и README.
- **Постобработка ответов:** автоматическое срезание markdown-обёрток (````markdown ... ````), которые часто возвращают модели.
- **Изоляция шагов:** флаг `--no-readme` для сохранения ручного README (doxdix не трогает «лицо» проекта).
- **Безопасность:** фильтрация файлов через `git ls-files` (обработка только отсортированных файлов, если доступен git).

**Работает напрямую с HTTP API LLM.** Единственная внешняя зависимость — `requests`.

**Название:** doxdix. **Расположение при разработке:** `/opt/dix/doxdix`.

## 2. Целевая структура документации проекта

```
project/
├── README.md              # корень, актуализируется LLM + детерминированная ссылка на LICENSE
├── CHANGELOG.md           # корень, генерируется из git (append-режим)
├── LICENSE                # plain text, doxdix НЕ трогает (только читает для ссылки в README)
├── docs/
│   ├── SUMMARY.md         # актуализируется LLM (всегда в docs/, независимо от --docs-dir)
│   └── modules/           # зеркало src/, актуализируется LLM пофайлово
│       ├── auth/
│       │   └── login.md
│       └── utils/
│           └── helpers.md
└── .doxdix/
    ├── cache.json         # кэш sha256 обработанных файлов
    └── backups/
        └── <timestamp>/
            ├── README.md
            ├── CHANGELOG.md
            ├── docs/
            └── manifest.json
```

**Правило зеркалирования:** относительный путь от `--src-dir` сохраняется, расширение меняется на `.md`, файл кладётся в `--docs-dir` (по умолчанию `docs/modules`). Примеры: `src/auth/login.py` → `docs/modules/auth/login.md`; `src/api/v1/users.ts` → `docs/modules/api/v1/users.md`. Если `--src-dir` не указан (обход всего проекта) — относительный путь от корня проекта, с префиксом `docs/modules/`.

**LICENSE:** plain text без расширения. doxdix его не изменяет. Используется только для определения типа лицензии и вставки ссылки в README.

## 3. Установка и обновление

**Установка:**
```bash
pipx install git+https://github.com/dneupokoev/doxdix.git
```

**Обновление:**
```bash
pipx install --force git+https://github.com/dneupokoev/doxdix.git
```

**Удаление:** `pipx uninstall doxdix`.

**Настройка:** Конфиг-файлы отсутствуют. Все параметры передаются через CLI-аргументы или переменные окружения (приоритет CLI выше).
- `DOXDIX_MODEL` — дефолт для `--model`.
- `DOXDIX_OLLAMA_URL` — дефолт для `--ollama-url`.
- `DOXDIX_API_KEY` — дефолт для `--api-key` (для OpenAI-совместимых API).

**Требования:** Python >= 3.10, установленный `requests>=2.31`, доступ к LLM (Ollama по умолчанию или OpenAI-совместимый endpoint), хотя бы одна загруженная модель.

## 5. CLI-интерфейс

```
doxdix PROJECT_PATH [options]
```

**Позиционный аргумент:**
- `PROJECT_PATH` — путь к корню целевого проекта (обязательный).

**Опции:**

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--src-dir PATH` | весь проект | Подпапка с исходным кодом (относительно PROJECT_PATH) |
| `--docs-dir PATH` | `docs/modules` | Куда класть документацию модулей |
| `--model NAME` | `DOXDIX_MODEL` или обязательный | Имя модели (Ollama или OpenAI-совместимой) |
| `--ollama-url URL` | `DOXDIX_OLLAMA_URL` или `http://localhost:11434` | Адрес LLM. Если URL содержит `/v1`, включается OpenAI-режим |
| `--api-key KEY` | `DOXDIX_API_KEY` или `dummy` | Токен для OpenAI-режима |
| `--extensions LIST` | `.py,.js,.ts,.jsx,.tsx,.go,.rs` | Расширения через запятую |
| `--exclude LIST` | см. п. 6.1 | Имена папок/паттерны через запятую |
| `--timeout SEC` | `300` | Таймаут одного запроса к LLM |
| `--num-ctx N` | `8192` | Размер контекстного окна (только для Ollama) |
| `--max-doc-tokens N` | `3000` | Если существующий .md больше — пропустить актуализацию |
| `--force` | выкл. | Игнорировать кэш хэшей: обработать все файлы, включая неизменённые |
| `--no-git` | выкл. | Не использовать git (не читать логи, не коммитить) |
| `--no-commit` | выкл. | Не делать git-коммиты после изменений |
| `--changelog-limit N` | `100` | Сколько коммитов брать для CHANGELOG |
| `--changelog-llm` | выкл. | Обогащать CHANGELOG через LLM |
| `--no-changelog` | выкл. | Не генерировать CHANGELOG |
| `--no-changelog-append` | выкл. | Перезаписывать CHANGELOG вместо дополнения |
| `--backup-dir PATH` | `<project>/.doxdix/backups` | Куда класть бэкапы |
| `--backup-keep N` | `10` | Сколько бэкапов хранить |
| `--no-backup` | выкл. | Отключить бэкап |
| `--restore TIMESTAMP` | — | Восстановить из бэкапа и выйти |
| `--init-license` | выкл. | Создать заготовку LICENSE (MIT), если нет |
| `--check` | — | Проверить LLM и модель, выйти |
| `--no-readme` | выкл. | **Не обновлять README.md** (шаг 2 пропускается) |
| `--log-file PATH` | `<project>/doxdix.log` | Файл лога |

**Коды возврата:** `0` — успех; `1` — были ошибки при обработке файлов; `2` — ошибка конфигурации (нет LLM, нет модели, неверный путь).

## 6. Логика работы

### 6.1. Шаг 0 — Сканирование и git-данные

`scanner.py` рекурсивно обходит `PROJECT_PATH` (или `PROJECT_PATH/--src-dir`), собирает файлы с расширениями из `--extensions`. Применяет исключения.

**Дефолтные исключения (папки):** `.git`, `.doxdix`, `node_modules`, `__pycache__`, `venv`, `.venv`, `env`, `dist`, `build`, `tests`, `test`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `target`.

**Дефолтные исключения (файлы/паттерны):** `test_*`, `*_test.*`, `*.min.*`, `*.spec.*`, `conftest.py`.

**Git-данные** (если `.git/` существует и не передан `--no-git`):
- `git log --no-merges -N --pretty=format:"%H|%s|%b"` (N = `--changelog-limit`) — для CHANGELOG.
- `git ls-files` — список отслеживаемых файлов. **Если git есть, обрабатываются ТОЛЬКО отслеживаемые файлы** (игнорируем черновики и мусор). Если git нет, обходятся все файлы (с учётом исключений).

Все вызовы — через `subprocess.run(cwd=project_root, capture_output=True, text=True, timeout=30)`. Ошибки git — `logger.warning`, продолжаем без git-данных.

**Результат шага:** список `Path` к файлам кода (отсортирован по строковому пути), dataclass `GitData {has_git, commits, tracked_files}`.

### 6.2. Шаг 0.5 — Бэкап

`backup.py` создаёт `.doxdix/backups/<ISO-timestamp>/`, копирует туда (если существуют):
- `README.md`, `CHANGELOG.md`
- всё содержимое `docs/`
- `manifest.json` со списком скопированных файлов и их `sha256`.

Формат timestamp: `2026-10-28T14-30-00` (ISO-8601, двоеточия заменены на дефисы). При коллизии — суффикс `-1`, `-2`.

**Ротация:** после создания бэкапа удалить старые, оставив `--backup-keep` последних (сортировка по имени папки).

**Восстановление:** `doxdix PROJECT --restore 2026-10-28T14-30-00` копирует файлы из бэкапа обратно в проект (перезаписывая) и выходит с кодом 0.

### 6.3. Шаг 1 — CHANGELOG.md

Выполняется, только если `has_git` и не передан `--no-changelog`.

`changelog_gen.py` парсит commit messages по Conventional Commits: `type(scope): description`. Маппинг:

| type | Секция |
|---|---|
| `feat` | Added |
| `fix` | Fixed |
| `perf` | Changed |
| `refactor` | Changed |
| `docs` | Documentation |
| `chore`, `ci`, `build`, `test`, `style` | пропустить |
| `BREAKING CHANGE` в теле или `feat!:` | Breaking Changes |

Нераспознанные коммиты — в секцию `Other` с пометкой `[non-conventional]`.

**Формат вывода** — Keep a Changelog. Секция `[Unreleased]` вставляется после заголовка `# Changelog`, существующие секции сохраняются ниже (если не передан `--no-changelog-append`, который перезаписывает файл).

**`--changelog-llm`:** сгруппированный список отправляется в LLM для переписывания в user-facing формулировки.

**Git-коммит** (если не `--no-commit`): `docs(doxdix): update CHANGELOG.md`.

### 6.4. Шаг 2 — README.md

**Если передан `--no-readme` — шаг полностью пропускается.**

Если `README.md` существует — прочитать. Если нет — `existing_content = ""`.

Промпт (см. п. 7.2): на вход `project_context` (первые 2000 символов README), список файлов проекта, последние 10 коммитов, `existing_content`. Задача: обновить разделы, описывающие код; сохранить вручную написанные разделы; не выдумывать флаги. Модель возвращает текст. 

**Постобработка (`_strip_code_fence`):** код срезает первую и последнюю строки, если они начинаются с ` ``` ` (модели любят оборачивать весь ответ в markdown-блок).

**Детерминированная вставка ссылки на LICENSE** (после LLM, отдельным шагом в коде):
1. Если `LICENSE` не существует — пропустить.
2. Если в README уже есть regex-совпадение `\[.*?\]\(\.?/?LICENSE[^)]*\)` (case-insensitive) — не трогать.
3. Иначе — определить тип лицензии по первым 20 строкам `LICENSE` (матчинг: «MIT License», «Apache License», «GNU GENERAL PUBLIC LICENSE», «BSD», иначе `None`).
4. Добавить в конец README:

```markdown
---
## Лицензия

Проект распространяется под лицензией [MIT](LICENSE). См. файл [LICENSE](LICENSE).
```

**Git-коммит** (если не `--no-commit`): `docs(doxdix): update README.md`.

### 6.5. Шаг 3 — docs/SUMMARY.md (init)

Если существует — прочитать. В LLM отправляется содержимое уже существующих `.md` модулей из `--docs-dir` (в том же формате и с теми же лимитами, что на шаге 5, п. 6.7), существующий SUMMARY и `project_context`. Если документации модулей ещё нет — передаётся список файлов кода как подсказка. Промпт: «дополни ссылками на модули, не удаляй существующие ссылки, не добавляй раздел про лицензию». Результат очищается `_strip_code_fence` и записывается.

**Git-коммит:** `docs(doxdix): update SUMMARY.md`.

### 6.6. Шаг 4 — Обход файлов (основной цикл)

Для каждого файла из списка (отсортирован по пути):

1. `rel_path` — путь относительно `PROJECT_PATH`.
2. `md_path` — по правилу зеркалирования.
3. Создать родительские папки.
4. **Проверка кэша:** вычислить sha256 кода. Если не передан `--force`, `md_path` существует и хэш совпадает с сохранённым в `.doxdix/cache.json` — пропустить файл (`skipped += 1`), перейти к следующему.
5. Прочитать `code_content`. Прочитать `existing_content` (если `md_path` существует, иначе `""`).
6. **Проверка размера:** если `len(existing_content) // 4 > max_doc_tokens` — пропустить файл, залогировать warning, увеличить счётчик пропущенных, перейти к следующему.
7. Сформировать промпт (п. 7.3). Отправить в LLM с `num_ctx` и `timeout`.
8. **Постобработка:** `_strip_code_fence`.
9. Записать ответ в `md_path` и обновить кэш: `Cache.set(rel_key, sha)`.
10. **Git-коммит** (если не `--no-commit` и `has_git`): `docs(doxdix): <rel_path>`.
11. Логировать: `[12/34] src/auth/login.py → docs/modules/auth/login.md ... OK (8.2s)`.
12. **При любой ошибке** — `log.error`, инкремент `errors`, **продолжить** со следующим файлом.

### 6.7. Шаг 5 — Финальное обновление SUMMARY.md

В LLM отправляется **содержимое** созданных/обновлённых на шаге 4 `.md` файлов (не просто их имена): для каждого файла — заголовок с путём относительно `docs/` и текст (не более 2000 символов на файл, суммарно не более 40000 символов; не влезшие в лимит файлы перечисляются путями без содержимого). Промпт («дополни SUMMARY ссылками на модули, опираясь на их содержимое; сохрани существующее») → очистить `_strip_code_fence` → записать. Если на шаге 4 не было создано/обновлено ни одного `.md` — шаг 5 пропускается без обращения к LLM. Git-коммит: `docs(doxdix): finalize SUMMARY.md`.

### 6.8. Завершение

Вывести итог: `Успешно: N, ошибок: M, пропущено: K. Лог: <path>`. Код возврата: `0` если `errors == 0`, иначе `1`.

### 7.4. CHANGELOG через LLM (шаг 1, `--changelog-llm`)

```
Ниже — сгруппированные по типам изменения из git-коммитов. Перепиши их в user-facing формулировки для CHANGELOG.md.

ПРАВИЛА:
1. Сохрани все факты. Не добавляй ничего, чего нет в списке.
```

## 8. LLM-клиент (`llm.py`)

**Функция:** `chat(base_url, model, prompt, num_ctx, timeout, api_key) -> str`.

**Автодетект режима:**
- Если `base_url` оканчивается на `/v1` или содержит `/v1/` — **OpenAI-режим**: `POST {base_url}/chat/completions`, заголовок `Authorization: Bearer {api_key}`. `num_ctx` игнорируется.
- Иначе — **Ollama-режим**: `POST {base_url}/api/chat`, `options.num_ctx` передаётся явно. Без заголовка `Authorization`.

**Обработка ошибок:**
- `timeout` — в `requests.post(..., timeout=timeout)`.
- HTTP != 200 — бросить `LLMError` с кодом и телом.
- Ответ без `message.content` (Ollama) или `choices[0].message.content` (OpenAI) — бросить `LLMError`.
- Пустой `content` — бросить `LLMError`.
- Возвращает `content.strip()`.

**Проверка при старте (`--check` и перед запуском):**
- `GET {base_url}/api/tags` (Ollama) или `GET {base_url}/models` (OpenAI).
- **Исключение для OpenAI:** если `/v1/models` возвращает 404 (некоторые прокси не отдают список), клиент возвращает пустой список `[]` и пишет warning. `cli.py` в этом случае пропускает проверку имени модели.
- Если списка нет и это не 404 — `LLMError`. Если модели нет в списке — код `2` со списком доступных.

## 10. Обработка ошибок (сводка)

| Ситуация | Поведение |
|---|---|
| LLM недоступен | Код `2`, сообщение, выход |
| Модель не найдена | Код `2`, список доступных |
| 404 на `/v1/models` | Warning, пустой список, проверка модели пропускается |
| Таймаут/HTTP-ошибка LLM | `log.error`, `errors += 1`, продолжить |
| Пустой ответ LLM | То же |
| Ошибка git-коммита | `log.warning`, продолжить |
| Нет `.git` | Работать без git |
| .md слишком большой | `log.warning`, `skipped += 1`, продолжить |
| Ошибка бэкапа | `log.error`, код `1` в конце, но продолжить |
| Файл не читается | `log.error`, `errors += 1`, продолжить |

## 12. Критерии готовности

- `pipx install --force git+<repo>` ставит команду `doxdix`.
- `doxdix --help` показывает все флаги (включая `--no-readme`, `--api-key`).
- `doxdix PROJECT --check` с Ollama проверяет модель и выходит.
- `doxdix PROJECT --check` с OpenAI-совместимым прокси без `/models` завершается успешно (warning, exit 0).
- На проекте с git: создаются `CHANGELOG.md`, `README.md`, `docs/SUMMARY.md`, `docs/modules/**/*.md`. Бэкап в `.doxdix/backups/<ts>/`. Коммиты после каждого изменения.
- Повторный запуск не ломает ручные разделы.
- `--restore` восстанавливает файлы.
- `--no-git`, `--no-commit`, `--no-changelog`, `--no-backup`, `--no-readme` работают изолированно.
- Ответы LLM не содержат обёрток ` ```markdown ` (срезаются `_strip_code_fence`).
- В SUMMARY нет раздела «Лицензия», в README — есть.
